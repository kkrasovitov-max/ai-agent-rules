# Схема №1 — Git-first

## 1. Архитектура

LOCAL → GITHUB → PRODUCTION

- LOCAL — разработка, редактирование кода, локальная БД и тестирование.
- GITHUB — источник правды для утверждённого кода, история изменений и контроль версий.
- PRODUCTION — исполнение сайта и хранение актуальных рабочих данных.

## 2. Правила работы ИИ-агента

- Все изменения кода выполняй локально.
- Используй Git для контроля версий.
- Не редактируй production-код напрямую.
- SSH используй только для согласованного деплоя и обслуживания.
- Самостоятельная SSH-диагностика production в данной схеме не предусмотрена.
- Не изменяй файлы, не относящиеся к задаче.
- Не перезаписывай существующие изменения пользователя.

## 3. Рабочий процесс

1. Изучи структуру локального проекта.
2. Проверь текущую ветку и состояние Git.
3. Проверь незакоммиченные изменения.
4. Проверь актуальность удалённого репозитория.
5. Проанализируй задачу.
6. Внеси необходимые изменения локально.
7. Выполни доступные тесты.
8. Покажи итоговый diff.
9. Подготовь commit.
10. После согласования выполни commit и push.
11. После согласования выполни деплой.
12. Проверь результат доступными средствами.

## 4. Контроль изменений

Используй команды:

    git status
    git branch --show-current
    git fetch origin
    git diff
    git diff --stat
    git diff --numstat
    git diff --check
    git diff --cached
    git log --oneline -10

Проверяй добавленные, изменённые и удалённые файлы.

Показывай добавленные и удалённые строки через git diff.

Учитывай новые неотслеживаемые файлы, которые ещё не отображаются в обычном git diff.

Добавляй в commit только файлы текущей задачи.

Не используй без отдельного разрешения:

    git reset --hard
    git clean -fd
    git push --force

При обнаружении конфликтов или расхождения версий сообщи пользователю.

## 5. Деплой

Основной маршрут:

LOCAL → COMMIT → PUSH → GITHUB → PRODUCTION

Пример ручного деплоя:

    ssh deploy@server
    cd /var/www/site
    git pull --ff-only origin main

Используй фактические параметры конкретного проекта.

При наличии CI/CD используй установленный механизм деплоя.

Перед деплоем проверь:

- Текущую production-версию.
- Утверждённую новую версию.
- Отсутствие несогласованных изменений на сервере.
- Необходимость миграций.
- Возможность отката.

Не передавай исходный код через rsync или scp в обход установленного Git-процесса.

## 6. База данных

- Локальная БД используется для разработки и тестирования.
- Production-БД содержит актуальные рабочие данные.
- Изменения структуры оформляй миграциями.
- Не перезаписывай production-БД локальным дампом.
- Не удаляй рабочие данные.
- Перед изменениями production-БД получи разрешение и обеспечь резервное копирование.

## 7. Медиафайлы

Медиафайлы и пользовательские загрузки синхронизируются отдельно от Git.

Для передачи допускается rsync.

Перед синхронизацией:

1. Проверь источник и назначение.
2. Определи направление передачи.
3. Настрой исключения.
4. Выполни dry-run.
5. Получи разрешение на запись.

Не используй rsync --delete без отдельного согласования.

## 8. Безопасность

Не добавляй в Git:

- .env с секретами;
- пароли;
- SSH-ключи;
- API-токены;
- конфиденциальные данные;
- дампы рабочих БД;
- логи с персональными данными.

Не обходи технические ограничения доступа.

Не выполняй потенциально разрушительные операции без разрешения.

## 9. Самостоятельность агента

Без дополнительного подтверждения разрешено:

- Анализировать локальный проект.
- Редактировать локальный код в рамках задачи.
- Выполнять локальные тесты.
- Анализировать Git diff.
- Подготавливать план деплоя.

Подтверждение необходимо перед:

- Commit и push.
- Деплоем.
- Записью на production.
- Изменением production-БД.
- Изменением системных настроек.
- Перезапуском сервисов.
- Удалением рабочих данных.
- Откатом production.

Если пользователь заранее явно разрешил конкретную операцию, повторное подтверждение не требуется в пределах этого разрешения.

## 10. Итоговый отчёт

Сообщи пользователю:

- Что сделано.
- Какие файлы изменены.
- Сколько строк добавлено и удалено.
- Какие тесты выполнены.
- Какие ошибки обнаружены.
- Нужны ли миграции.
- Статус commit.
- Статус push.
- Статус деплоя.
- Известные риски.
- Способ отката.

Не утверждай, что операция выполнена, если она фактически не выполнялась.

## 11. Главный принцип

Разрабатывай локально.

Храни утверждённый код в GitHub.

Разворачивай на production только проверенные версии.
